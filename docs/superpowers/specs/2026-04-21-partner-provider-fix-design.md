# Design: Fix `partnerProvider` — Partner Info Not Showing After Pairing

**Date:** 2026-04-21  
**Status:** Approved

---

## Problem

After two users successfully pair, the home screen partner info section stays empty or shows a loading spinner indefinitely. The pairing transaction itself is correct — both user documents receive the `coupleId` in Firestore. The bug is exclusively in how `partnerProvider` fetches the partner's data after pairing.

### Root Cause

`partnerProvider` (a `FutureProvider`) depends on `currentCoupleProvider` (also a `FutureProvider`), which depends on `currentUserDataProvider` (also a `FutureProvider`). This one-shot chain can serve stale Firestore cache data that does not yet include the `coupleId`. Even when `ref.invalidate` is called from the pairing screen, re-execution may still hit the local Firestore cache and return the pre-pairing state.

A reactive alternative already exists: `coupleProvider` is a `StreamProvider` that watches `userProvider` (Firestore real-time stream). It correctly updates the moment the user document gains a `coupleId`. `partnerProvider` does not use it.

---

## Scope

- **In scope:** Rewriting `partnerProvider` in `lib/features/auth/presentation/auth_providers.dart`.
- **Out of scope:** The pairing transaction (`PairingService`), the router (`app_router.dart`), all UI screens, `coupleProvider`, `userProvider`, and `currentCoupleProvider`.

---

## Design

### Provider dependency chain — before

```
partnerProvider          (FutureProvider<UserModel?>)
  └─ currentCoupleProvider  (FutureProvider<CoupleModel?>, one-shot, stale cache risk)
       └─ currentUserDataProvider  (FutureProvider<UserModel?>, one-shot, stale cache risk)
```

### Provider dependency chain — after

```
partnerProvider          (StreamProvider<UserModel?>)
  └─ coupleProvider         (StreamProvider<CoupleModel?>, real-time Firestore stream)
       └─ userProvider          (StreamProvider<UserModel?>, real-time Firestore stream)
```

### Implementation

Convert `partnerProvider` from `@riverpod Future<UserModel?>` to `@riverpod Stream<UserModel?>` in `lib/features/auth/presentation/auth_providers.dart`.

Logic inside the new provider:

1. Watch `coupleProvider` using `ref.watch(coupleProvider)`.
2. If the async value is loading or error → yield null (no partner yet).
3. If data is null (no couple) → yield null.
4. If data has a couple → find the partner UID: the member in `couple.members` that is not `currentUser.uid`.
5. Fetch the partner's user document from Firestore via `UserRepository.getUserById(partnerUid)`.
6. Yield the result.

The stream re-evaluates automatically whenever `coupleProvider` emits a new value (e.g., after pairing, status change, or app restart).

### Home screen compatibility

`home_screen.dart` already uses:
```dart
final partnerAsync = ref.watch(partnerProvider);
// ...
partnerAsync.when(data: ..., loading: ..., error: ...)
```

Both `FutureProvider` and `StreamProvider` expose `AsyncValue<T>` — the call site is identical. **No changes to `home_screen.dart`.**

---

## Error handling

| Scenario | Behaviour |
|---|---|
| Not authenticated | `currentUserProvider` returns null → partner stream emits null |
| Not paired | `coupleProvider` emits null → partner stream emits null |
| Partner UID not in members | `firstWhere` with `orElse: () => ''` → empty string → emit null |
| Firestore fetch fails | Exception propagates as `AsyncError` in the stream |
